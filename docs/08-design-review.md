v0.3 更新：对照了 Fable v3 的主规范。全文上链、序号、MTP、历史载体恢复已与本套主线收敛；期限型授权已按用户选择纳入首版。仍需区别当前缺口与历史反例：旧混合输入 ACP 构造不证明新白名单被攻破；每日/收尾日志问题已经被 Fable v3 删除，不能继续描述为其当前行为。现有取舍见 [09](09-design-update.md)，授权规范见 [11](11-authorization.md)。

## 1. 不采用的通用推论

| 推论 | 为什么不充分 | 本版处理 |
|---|---|---|
| 所有 input locks 都视为投了该票 | 某些 lock 能在无主人签名时解锁；交易有效不等于每个 owner 同意投票 | [协议 §5.2](03-protocol.md)：逐 adapter 验证实际授权及承诺覆盖 |
| 允许混合输入时，所有输出都回 input locks，且只有一个 marker，即可消除被动投票 | 这些约束控制资金去向，不能证明每个输入主体签过选择 | 见下文旧规则 ACP 反例；最新单 lock 约束已挡住该具体构造 |
| 未知 lock 或 JoyID 子密钥走交易通道天然安全 | 未审查的 lock 可能有免签、代理、管理员或宽松签名路径 | [钱包矩阵](05-delivery.md)：未验证即未支持，交易通道同样要验收 |
| Omnilock args 只需匹配身份前缀 | 前缀没有表达全部模式与附加约束 | [协议 §5.1](03-protocol.md)：匹配完整 script 与明确模式，动态授权核对历史状态 |
| 自报 Issued 与收票时间相差不超过十分钟即可客观排序 | 两个时钟均不能提供独立及时性证明；运营者可回填、延迟 | 已签锚点表示修订先后，链收录判时窗；A 明确接受运营时间见证的信任 |
| 结束快照可确定地称为零规则变更 | 规则“当前”与历史查询行为没有完整统一；精度和提款阶段也有边界差异 | [兼容矩阵](01-research.md)：保留本金公式，时点等须公开澄清 |
| 消息投票必然应采用开始快照 | 消息格式与资产快照政策相互独立；开始快照会排除期间新增存款 | [分支 §6](06-alternatives.md)：列出差异，不借钱包适配改变票权 |
| 42 epochs 精确等于七天，两家 RPC 一致就完全独立 | epoch 时长浮动；RPC 可共用源，返回一致不证明全集正确 | [协议 §8–9](03-protocol.md)：固定时钟政策，从自己的已验证历史重建 |
| 收尾 root 上链就解决了数据完整与可用性 | root 不能找回被隐藏的选票，也不证明漏掉的票不存在 | [分支 §2–3](06-alternatives.md)：区分承诺、公开原文和完备性 |
| 输出 cell 的 lock 是运营方，就证明锚定由运营方发出 | 任何人可以向该 lock 创建输出，未必需要其签名 | 单独验证声明内容与发布权限；载体地址不作认证 |
| 授权一年但不能转账，就没有资产相关风险 | 被盗密钥能改变投票并影响人工拨款，撤销未必撤回旧票 | 首版已纳入设计；11 定义期限、历史验权、owner 接管与安全恢复，真实实现与验收尚未完成 |

这些判断针对通用推论，不表示相应钱包或上游项目已被证明存在可利用漏洞。

## 2. 旧混合输入归属规则的 ACP 反例

假设 V 的 DAO 存款由一个 ACP lock 控制，V 还拥有相同 lock 的普通无 type、空 data cell。攻击者 A 可以构造这样的抽象交易：

* 输入为 A 的普通资金 cell，以及 V 的普通 ACP cell；不消费 V 的 DAO deposit。
* 输出保留 V 的 ACP cell 并增加满足最低支付条件的 capacity；其余是 A 的找零和 A 控制的投票 marker。
* A 为自己的输入签名；V 的 ACP 输入走接受支付的免签路径。

它同时满足“全部输出 lock 出现在输入集合”和“只有一个 marker，其 lock 出现在输入集合”。若计票将所有输入 lock 都认作投票者，V 的 DAO 本金便会被附加到 A 选择的票上，即使 V 从未签过票。

这是根据协议构造的设计反例，不是本次已广播或通过 CKB-VM 跑完的交易 fixture。ACP 免签支付路径由 [RFC 26](https://github.com/nervosnetwork/rfcs/blob/62a6e08e16a995ab94562581978ceac3726c31e6/rfcs/0026-anyone-can-pay/0026-anyone-can-pay.md#unlock-rules) 明确定义；Omnilock 还有独立的管理员、ACP 等模式，见 [RFC 42](https://github.com/nervosnetwork/rfcs/blob/62a6e08e16a995ab94562581978ceac3726c31e6/rfcs/0042-omnilock/0042-omnilock.md#administrator-mode)。

修正是证明“这个 owner 确实授权了这份选票承诺”，不是再增加一条找零地址规则。该反例应在未来交易 adapter 上线前成为真实 CKB-VM 负向用例。

Fable v2 的“全部输入同一 lock 且等于 marker lock”排除了上面的 A/V 混合输入；v2.1 又加入模式白名单，方向正确。本方案吸收单 lock 模板作为 C 的额外约束，但仍不以它代替授权审查。例如一个自定义 lock 若不认证输出数据，仅验证它允许的其他条件，单 lock 自转账也不能推导出它认证了投票选择。此处是通用逻辑反例，不是宣称某个白名单钱包存在该漏洞。

### 2.1 输出地址不能认证发布者

Fable v3 详细设计曾以 `cell lock ∈ operator_locks` 判断结果与延期记录有效，并对提案记录使用输出 lock 归属条件。marker 仅检查格式、无许可创建，因此攻击者可用自己的输入创建一个付到运营方 lock 的 marker，满足这个地址检查，但运营方未签署其中内容。

CKB 仅为 inputs 执行 lock，输出 lock 不是创建者签名。[RFC 22](https://github.com/nervosnetwork/rfcs/blob/62a6e08e16a995ab94562581978ceac3726c31e6/rfcs/0022-transaction-structure/0022-transaction-structure.md#lock-script) 因此不能据此认证官方锚定。该错误会使官方记录认证失效，并可能影响规范 PROP 的选择；Fable v3 已删除收尾日志，不再用旧的收尾攻击描述这一版本。此处是规范层面反例，尚未进行 CKB-VM fixture 验证。

本版任何人可发 carrier；投票依 owner 签名，提案依 proposer 签名，声称官方来源的声明独立验证主体、用途、内容与权限。有效数学结果由完整复算产生，不以发送者标签替代验证。

### 2.2 缺少收尾记录时不能接受局部正常结果

Fable 旧版曾规定“收尾锚定缺失时取最后每日锚定并报告异常”（v3 已删除）。这种做法可用于诊断，但不得据其给出正常通过并付款；最后一天已接收的票可能被排除。B 的有效票集合取自规范链窗口，收尾记录不是准入门槛。链历史不足时输出 DATA_INCOMPLETE，复核期补数据而不补投。此项已写入本版协议和结果页状态。

### 2.3 Fable v3 评审后写入的修正

* 按签名 key 全局先取最高序号会使 A 的过期新票挤掉旧有效票，虽然同 key 的 B 授权还有效；11 按 owner 验权后排序。
* 主路径 key 由第二个在线钱包保管，本机公钥或通用 passkey 是可选候选；不强制称 key 具有 signer_lock，11 分开 key_id、owner_id、授权版本。
* 选票序号不能替代授权控制的排序；11 明确锚点较早的控制、同锚点冲突、续期/更换、自然到期与安全撤回。第二轮评审又发现，由签名者填写的控制序号可被一次签满，现已改为按锚点高度排序。
* 直接通道和签名通道共同检查完整 `[start,end)`，过早无效出现不占位置。
* 核心规则/授权全文必须可恢复；浏览器给定数据包验算、多个 RPC 一致、多个确认地址均不是全集证明。
* Ledger 只显示前 61 字节，固定标题作首行等于什么都核对不了；现已改为 ASCII 摘要首行，但只显示部分内容不等于完整核对。passkey 的 RP ID 范围不等于任意镜像可调用。这些仍需真机与故障演练。

这些是规范分析与设计修正，没有把尚未实现的攻击 fixture 描述成已跑完的安全测试。

## 3. 当前路线的准确含义

* **A**：链下签名和公开日志，明确保留收票与时钟信任。
* **B（推荐）**：消息签名，链上发布完整 envelope，独立历史复算。仅上链日志 root 不等价。
* **C**：逐 lock 审查的用户交易投票通道，不承诺任意 lock。
* **D**：原生合约或历史证明验证最终结果，执行层另行审查。

“链下收票 + 用户交易兜底”也是可以评估的组合，但默认链下集合仍受运营者影响；不能因为另有交易通道，就声称默认路径全部选票已获得 B 的完整公开保证。也不能因为存在合约，就略过聚合集合完备性的验证。

## 4. 研究结果与产品保证的边界

钱包 SDK 有签名函数，只能证明代码路径存在；不能证明真实设备可清楚显示本协议长消息，也不能代替互操作测试。一次实时 indexer 抓取可观察脚本分布，不能自动成为有完备性证明的历史状态。定向搜索未找到某组件源码，也不单独证明该组件必然闭源。

本版钱包覆盖仍以 PoC 和适配矩阵为门槛，没有把补充研究的代码观察升级为全钱包承诺。模型测试验证抽象计票性质，没有模拟签名、完整 CKB 共识或真实钱包。完成初步方案设计与允许主网上线是两个分别核验的里程碑。
