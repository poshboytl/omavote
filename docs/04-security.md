# 安全分析与验证计划

本文件分析推荐路线 B：签名选票、链上完整存证、独立链下复算。这里的攻击分析是设计推导；提到上游行为时参见 [研究依据](01-research.md)。没有声称已经审计完成任何主网实现。

## 1. 保护对象与对手

保护对象依次是用户本金和钱包权限、真实投票意图、票权与结果的正确性、及时参与的能力、公开证据的可获得性、必要的身份隐私。

假设攻击者可以创建任意网站账号、任意钱包和交易，控制一个或所有官方后台，延迟或重放收到的签名，返回伪造 RPC 数据，购买或借入真实 CKB，运行恶意镜像前端，制造垃圾载荷；部分场景还考虑矿工短期审查和链重组。

不假设密码算法被攻破或 CKB 的完整共识安全已经失效。用户主动授权的密钥泄露、凭真实资本获得的投票权，不能仅靠应用程序辨认真正经济受益人。

## 2. 逐项攻击矩阵

| 攻击路径 | 为什么会出错 | 推荐防护 | 剩余边界/验证要求 |
|---|---|---|---|
| 同地址解绑后换账号再投 | 按网站账号缓存权重 | owner=完整 lock；每个 outpoint 最多一次 | 需要实际复算，不靠账号唯一约束 |
| A 投票后提款、转 B、再存再投 | 将不同时点余额相加 | 所有权重按统一截止状态结算 | 最后实际持有者仍可合法投票 |
| 历史存款重复累加 | 用累计 DAO event 代替余额 | 创建/花费状态重放；只计 active deposit | 不能仅查 today 的 live-cell API |
| withdrawing 仍被计票 | 只核对 DAO type，不看 data | type 精确匹配且 data 恰为八个零 | phase-1 政策须先确认 |
| A 的签名附 B 的地址 | 验签和地址关联分离 | 从签名身份推导/验证完整 lock | JoyID、动态授权、特殊锁需单独 adapter |
| ACP 免签 input 冒充授权 | input 出现被当作 owner 同意 | 验证明确 owner 认证路径；不通用放行 | 必须构造真实 CKB-VM 攻击用例 |
| 一名多签成员冒充整个多签 | 把一个 key 等同整组权限 | 原配置、阈值、必签成员全部匹配 | 不支持则公开说明，不能降为单签 |
| 同 key 跨 lock 类型误合并 | 只比 args 或 EVM 地址尾部 | 每个完整 script 独立验权、计权 | PW/Omnilock 的便利汇总需显式证明 |
| 旧签名用于新提案/新网络 | 缺少域分离 | genesis、DAO、poll、rule、adapter、action 全部签入 | 不接受历史 Metaforo 绑定签名当选票 |
| 中继延后发布旧选择 | 以最后 HTTP 时间或入链顺序判最新 | 签名锚点；相同 body 去重 | 锚点相同的两张不同票冲突，需用户签新票 |
| 重复 envelope/签名变体 | 按签名字节或 tx 计次数 | body hash 去重，验签后占位 | 无效签名不得污染去重表 |
| 无效早期广播“抢占” ballot_id | 去重早于时间/资格核验 | 记录最早有效出现，而非最早看到 | 加入迟到、过早、无余额后重播测试 |
| 中继改选择、规则或标题 | 用户签的是无关登录 nonce，或摘要与显示文字脱节 | 对确定性可读票面签名，其中包含完整 body hash；manifest hash 固定 | verifier 独立重建文本；诱骗用户签错提案仍是风险 |
| 钱包票面与机器 body 表达不同意思 | 未核对可读字段与提案 | 标题、预算、收款方、选择、截止均按固定渲染器重建 | Unicode 控制字符、金额格式、截断、换行均有负向向量 |
| 给运营方地址发 marker 冒充官方声明 | 把输出 lock 当成发送者签名 | 载体谁都可发；官方声明另验用途绑定的签名与权限 | 结果仍须独立复算，官方标签不能替代 |
| 中继收到但不发 | 接收方控制可用性 | 可携带 envelope、多中继、帮助者代付；不强迫用户付费 | 签名 receipt 证明违约，不保证票能赶上截止 |
| 只存 Merkle root，藏掉票 | 完整数据在私有库 | 完整 body+proof 进入公共交易历史 | 仍需要可用的历史节点/备份 |
| API 故意漏掉反对票 | 信任列表完备性 | 扫描规范区间全部相关历史，独立实现复算 | 单张 inclusion proof 不能证明没有漏票 |
| 伪造初始快照 | 只验证快照 root 与后台一致 | 从 genesis/自行验证 checkpoint 重建 | 发布多份一致 root 也不替代正确性 |
| 投票后正文、预算或接收地址被换 | 论坛正文可编辑，前端读最新版本 | manifest 固定各 hash 和接收 script | 人类还需确认提案就是愿意支持的内容 |
| 假冒同标题“官方投票” | 密码学不提供治理合法性 | 官方目录、论坛回链、明确 poll_id 与 `#` 短编号、开票前收录的协调者准入记录 | 协调层的真实性仍需治理信任 |
| 浮点、小数截断或阈值边界攻击 | `Number` 精度、逐层舍入、百分比显示 | 原始整数、交叉乘法、版本化 precision | 兼容政策不清时不能发布正式结果 |
| RPC 超时被当零权重 | 错误处理 `unwrap_or_default` 类路径 | fail closed，输出 DATA_INCOMPLETE | 可用性攻击仍可拖延结果，不能伪装成确定结果 |
| 截止后把消息时间回填 | 用户/服务器时间不可信 | 实际链上收录位置与固定 clock | 真实墙钟与链时间的偏差需公开 |
| 深重组使票或存款消失 | 只看块高，不固定 hash | block hash、回滚日志、确认和复核窗口 | PoW 不存在绝对最终性；已付款难追回 |
| 垃圾票耗尽免费中继 | 开放赞助可被任意地址调用 | 早验签、资源上限、补贴预算、按 owner 限流 | 社会账号验证不能偷偷变成投票资格 |
| 超大批次/恶意 proof 拖垮 verifier | 未限制解析、循环或内存 | 固定尺寸和复杂度上限、流式解析、超时 | 不能为省资源忽略合法大户的 cell |
| 错误升级改变旧结果 | 动态加载策略/adapter | 提案固定规则和版本，旧版可重建 | 发现旧版本漏洞需公开争议处置 |
| 投票 key 失窃、被诱导长期授权 | key 可影响授权期内多个提案 | 期限、owner 直接接管、默认安全撤销未结束代理票、钱包恢复或 owner 重新授权；本机候选可选加密备份 | 不能撤回已经结束并执行的治理结果 |
| 先选 key 最新票再验 owner 授权 | 过期新票挤掉有效旧票 | 逐 owner 验收录时 grant，之后按授权与选票锚点排序 | A/B 不同期限与部分恢复必须测 |
| 锚点较早的 GRANT 延迟发布 | 已撤销授权可能被恢复 | 控制消息按签入的锚点高度排序，锚点较早者无状态作用；24 小时发布期限 | 同锚点不同控制建立安全撤回屏障 |
| 钓鱼签下的 GRANT 无法撤销 | 若按签名者填写的序号排序，一份最大序号的 GRANT 会让 owner 再也签不出更高者 | 不使用控制序号；owner 之后签出、锚点更高并及时收录的控制消息生效 | 恢复客户端须防止节点落后导致锚点回退；钓鱼生效期间的代理票靠安全撤回屏障处理 |
| 高代理序号阻止 owner 恢复 | 直接票与代理票共用、或一次签满某条序列 | 独立直接序列，owner 优先；选票只按锚点排序，没有可签满的序号 | 直接接管该提案后不自动交回代理 |
| 扣留早签的票，截止前才发布 | 若按签名者填写的序号决胜，旧签名可靠大数字反超 | 选票只按锚点排序，锚点取签名时已验证的最新块；同一块内的不同票为冲突 | 节点落后时不成立；恶意页面让用户之后再签攻击者的选择仍会生效 |
| 中间改票未发布，最新改票被卡住 | 若要求序号连续，换中继发布最新票前须先发布已放弃的版本 | 按锚点排序，最新改票可单独交给任何发布者 | 仍需在截止前收录 |
| 旧流程记录覆盖新状态 | 按最后收录决定治理状态时，旧声明可被原样重发，或扣住后首次发布 | 流程记录签入锚点与发布期限；同一 record_id 只认首次；同类记录按锚点取最新 | 委员会自己签出互相矛盾的记录时显示冲突，治理状态按暂停执行处理 |
| 安全撤销与新 GRANT 乱序上链 | 新 GRANT 先上链时，撤销因锚点更早被判过时，屏障失效 | 一步完成的 GRANT+CANCEL；单独撤销后须确认生效再授权 | 不遵守顺序的客户端仍可能保留旧票 |
| 收窄提案格式清单复活旧授权 | 按提案过滤控制消息会忽略已发布的撤销 | 控制消息按全局只增不减的控制格式集合处理，提案清单只过滤选票 | 无法识别的控制格式报告不完整，不能跳过 |
| 其他网站请求在线钱包签选票 | 通用钱包对任意网站签文本，消息不绑定来源；GRANT 公开 key 与票权 | 引导独立投票账户、每张代理票提示 owner、owner 直投优先与安全撤销；B 的尾盘代理截止待定 | 协议层无法区分正版与钓鱼网站 |
| 某 adapter 被发现可伪造 | 授权控制或选票可被冒签 | adapter ID 不可修改；后续提案不再列入，即排除用它签的选票及以它签署的 grant 为依据的代理票 | 仍接受该格式的提案（含已开票者）可能计入伪造票，须发布 HOLD_EXECUTION 并按治理处置；控制格式被攻破时伪造控制可使代理投票失效，停用规则另定；已结束提案不追溯 |
| 撤销后回退更老代理票 | 只删除最后一张票 | 安全屏障排除该 owner 的所有先前代理票 | 自然到期/STOP_ONLY 保留旧票，必须清楚区别 |
| 官方域失效、passkey 无法在镜像调用 | 把钱包连接或 RP ID 凭证当作任意跨站可用 | 真机重连/恢复演练、owner 重新授权；本机候选另测备份导入 | 不承诺所有 key 形态无感跨站 |
| 前端/依赖被植入盗币逻辑 | 用户信任域名和构建产物 | 静态可复现包、CSP、锁依赖、最小钱包调用 | 源码开源不证明域名正在运行那份源码 |
| 免费投票变成经济诱导 | 赞助行为被混作投票奖励 | 所有选项同等代付，不按选择给资产 | 与既有禁止空投规则的适用需公开确认 |

其中时间、快照与日志完整性问题，比选一种更复杂的树结构更优先。

## 3. 本金安全

### 3.1 默认消息路径

用户签有明确前缀、网络与用途域的消息：选票绑定具体提案，授权控制绑定 DAO、owner、policy、目标密钥及期限；中继自己花手续费。不存在给 Omavote 的 token approve、合约本金存入、DAO 解锁、seed 导入或资产转移授权。默认签名验证采用钱包现有的消息签名域，不使用裸 `signDigest` 假装消息签名。

域分离只能降低签名跨用途重用风险，不能防止假网站切换到真实交易请求。前端清楚显示本次动作类型；发布版本的允许钱包方法做小范围控制，消息路径不需要调用发送资产方法。独立客户端在用户签名前可以核对原文。

默认消息路径实际签署可读挑战。标题、预算、收款地址与选择由冻结 manifest/body 确定并进入签名字节；验证器不能相信 envelope 自带的独立显示文本。钱包无法展示关键字段时，不得自动改用裸摘要签名或删掉字段。每种签名文本的首行都是不超过 60 字节的 ASCII 摘要，使只显示前 61 字节的设备也能核对动作、提案编号或目标地址、预算或到期日；这是有限的显示保证，16 位编号与地址缩写只是辅助标识，其余字段仍依赖电脑端核对全文。首版已纳入默认一年（365 链日）、最长 365 链日的公开期限授权，本地保存地址清单本身仍不构成授权。可选 WebAuthn 是单独定义的 body challenge 路径，必须依赖受审查客户端显示并确认内容；认证器通常不展示提案文本，不能将其宣称为与硬件可读签名相同的保证，见 [11 §4](11-authorization.md)。

### 3.2 交易路径

交易通道风险更大，因此作为独立能力验收：资产选择器不把 type 非空的 cell 作为手续费来源；拒绝 DAO 输入；拒绝陌生收款 lock、意外输出数据、额外资产与超过上限的手续费。C 的研究候选采用单 owner lock 输入、选票载体与找零全部回同 lock 的自付模板；它不符合免费用户流程，不能标为首版已支持。赞助 C 必须独立验收资金归属与签名覆盖，不以未经审查的共同出资补齐产品要求。不允许签后补入 fee input；未来共同出资需签前协商完整交易并单独审查覆盖范围。B 由第三方承载已签 envelope 是不同机制，不从付款者推断投票者。

免费产品路径的普通载体容量由中继/帮助者出资，发布者只能回收自己的资金；外部自愿发布交易不改变用户免费要求。若将来为了第三方自动清理引入专用 lock，则新增的退款规则、手续费扣除和抢跑风险必须另行审计。首版不为了省一次 reclaim 操作引入这样的合约。

## 4. 正确计票与完整计票是两件事

有十张正确签名的票，加法正确，只证明“这十张怎么算”；它不能证明本应计入的第十一张不存在。

三个独立问题都需要回答：

1. **授权**：这张票是否由该资产主体合法授权？
2. **状态**：该主体在所规定时点是否拥有这些 active deposit？
3. **完备性**：是否收集了截止前全部公开有效票和所有相关状态变化？

推荐 B 用完整链历史给第 3 点提供可重建的公共边界。A 则仍依赖收票日志的完整性和时点见证；D 可以用状态规则或历史证明压缩这些检查，但不能删除问题。

委员会需要看到确定的错误证据而非口头举报。可重现材料应指出：poll hash、规则 hash、区块 hash、具体 outpoint / ballot_id、两个 verifier 的差异及最小复现步骤。证据缺失时标注不确定，不通过人工填入一个猜测余额“修好”结果。

## 5. 无法靠换工具消除的经济与治理问题

### 5.1 巨鲸、借币和关键时刻入场

线性本金票权意味着大持有者有大权重，地址拆分不会降低或增加其总线性权重。不能把地址数量展示成“独立人数”。新存款在投票期间获得资格若符合规则，就不能因其影响结果而临时剔除。

直接把同一笔流动 CKB 做 DAO 存款后在同一交易内自由取回，受到 DAO 状态转换和提款周期约束，因此不能照搬 ERC-20 快照的闪电贷模型。但这不阻止较长周期借贷、购买控制密钥、场外购买投票授权、托管机构用客户存款投票，或用金融对冲降低资本风险。已有存款临近可提现时点也不能简单认为一定还要锁满新的一整个周期。

若只有攻击者投票，预算 B 的 quorum 要求约束其有效本金至少为 `3B`。存在全部反对的其他权重 N 时，按包含边界的 51% 规则，其 YES 权重 Y 需同时满足：

```text
Y >= max(3B - N, ceil(51N / 49), 0)
```

这是门槛推导，不是实际攻击成本估价。真实资本可以重复参与多个独立提案：M 个各预算 B 的提案，不要求锁住 M×3B 的独立本金。软件不能把“每提案 quorum”误述为对整个金库的资本担保。

### 5.2 买票和胁迫

公开可验证的签名本身是可展示的收据，能够被用来证明投了哪一票。可改票只在买票者不能约束最终改票时增加难度，并不彻底防买票。Commit–reveal 也不自动解决可交易收据问题。

MACI、无收据投票、匿名凭证与 ZK nullifier 都可成为独立研究方向，但会改变信任、隐私和使用流程；本设计不把它们作为首版安全承诺。

### 5.3 托管、交易所与衍生资产

“有私钥或有效控制权”证明的是脚本权限，不证明法律或经济上谁拥有全部收益。交易所托管、iCKB/dCKB 或其他池化存款，需要各自的所有权和权重分配政策。首版不同时计底层 deposit 和映射代币，不因为 ticker 里含 CKB 就赋予票权，也不让服务端给某机构临时打折。

### 5.4 讨论阶段 Sybil

30 个论坛赞可能被多个账号影响，这是提案准入流程的问题。资金加权计票的唯一性不能证明每个论坛赞来自不同真人；本工具保留论坛审查记录与争议入口，不自动添加 KYC 或把某个 DID 当作一人证明。

## 6. 隐私

公开票权符合当前基础规则，但不应额外收集真实姓名、邮箱或社交账号。多地址仅在本地清单展示时不自动公开组合关系；但多个 owner 授权同一个 key 会在公开历史中关联这些地址。授权前必须说明这一隐私代价，不能仍宣传多地址组合不可关联。

中继可能观察 IP、提交时间和地址关系；默认不持久记录与选票关联的 IP，限流使用短期计数，必要故障日志最小化留存并公布保留期限。关闭广告和第三方行为分析。选票和地址进入链后无法删除；产品在确认投票前明确显示这点。隐藏昵称不等于匿名，公共链资金流仍可能关联身份。

## 7. 复核与失败处置

| 状态 | 允许的行为 | 不允许的行为 |
|---|---|---|
| RPC 不一致/数据缺失 | 暂停确定结果、补全数据、独立重跑 | 把缺失当零、挑有利源、用昨日锚定或部分票作为正式结果 |
| 存在计票实现 bug | 固定原数据重算、公开差异和版本 | 修改原签名票或暗改原规则 |
| 中继未及时发布 | 使用尚在窗口内的其他出口；公布 receipt | 在截止后伪造收录时间补票 |
| 发现资格或时间政策歧义 | 按既有流程裁定、必要时废止重开 | 管理员在结果已知后自由选公式 |
| 已确认后深重组 | 标记争议、暂停未执行支付、披露影响 | 继续宣称旧结果仍有绝对链保证 |
| 前端供应链事故 | 撤下受影响构建、发布 hash 和安全替代入口 | 让“紧急升级”拥有改票或资金权力 |

紧急暂停应暂停展示确定结论和执行，不赋予后台篡改原始选票的能力。无法阻止人们继续往公共链发布数据；这些数据仍按原先固定的窗口判定。

本版不依赖运营者收尾 root 定义选票全集，也没有默认故障延期。争议标记与治理处置另列于数学结果，不可让管理员删票或覆写 `passed`。期限型授权已纳入首版，按 [11](11-authorization.md) 执行自然到期、STOP_ONLY、安全撤回、授权冲突和多地址恢复；完整控制历史公开。恢复仍须及时上链，密钥丢失不是自动延期或截止后补票的理由。

## 8. 必须完成的验证

### 8.1 已在本仓库覆盖的模型层

研究模型检查：最终快照避免循环计权、同一主体重复票不增加本金、改票与重放顺序、撤票、同序号冲突、临时无资格的票不能污染去重、截止前后状态、提款状态、小额精度和整数阈值、数据不完整时失败、重组后重新计算。另以随机事件生成检查总量守恒和重复广播不改变结果。

它把网络、密码学、原始 CKB 解码和时钟边界作为前置条件，**没有证明签名正确、共识安全、钱包可用或真实 RPC 历史完整**；也没有实现 v0.3 的代理授权、锚点排序、安全撤回屏障、流程记录和密钥库。

### 8.3 审计组织

应有至少一套不同实现者编写的参考 verifier，并由不负责日常中继的人运行比对。共享 schema 和测试向量合理，逐行复制同一个计票函数无法排除共同实现错误。

验证器与运营程序一起交付；不能等平台上线后再把独立验证作为社区自愿补齐的工作。正式启用前，公布已知限制和未支持的 locks。任何新增本金托管或金库自动执行功能，都重新进入合约与经济安全审查，不沿用本设计“无本金合约”的风险结论。
