评审进展：Claude 两轮评审提出的冻结阻塞项已写入规范（[09 §9](09-design-update.md)），同事两次复核指出的问题也已修正（[09 §10–11](09-design-update.md)）：授权控制、选票与流程记录都按签入的锚点排序，锚点一律取最新块，选票不设序号；控制消息按全局只增不减的控制格式集合处理，提案清单只过滤选票；GRANT 可一步撤回旧代理票；签名文本加入首行摘要；补齐提案签名、流程角色与确定性开票确认。这些修订尚未经过可执行测试或实现验证，V2 冻结条件见 [05 §8](05-delivery.md)。用户 A–E 决策见 [09 §6](09-design-update.md)：默认期限为一年，C/D/E 已确认方向，B 首版不启用。Fable 草稿已删除，本目录是唯一设计基线；当前稿仍不是已冻结的实现规范。

## 1. 阅读顺序与已定范围

先看 [09：决策记录](09-design-update.md) 和 [10：用户流程](10-user-journey.md)，然后联合审查 [03：主协议](03-protocol.md)、[11：授权协议](11-authorization.md)。安全边界见 [04](04-security.md)、[08](08-design-review.md)，实施门槛见 [05](05-delivery.md)。

已选：Nervos DAO 本金线性票权；完整签名数据上链；中继代付与开放发布，用户免费为硬约束；首版期限型授权，默认一年（365 链日）、最多 365 个链时间日；Neuron 授权第二个在线钱包，由它保管 key 并签具体选票；本机密钥可选；owner 接管和安全撤回；默认普通载体；固定小范围规则；数学计票、验证状态与治理处置分开；既有多签人工打款。

正式切换的治理程序由用户和既有 DAO 流程负责。评审不需要重选“是否支持一次授权”或重新设计金库；若发现约束冲突，给出具体例子与修正建议即可。

## 2. 重点问题

| 领域 | 需要检查的问题 | 规范位置 |
|---|---|---|
| 授权主体 | key_id 与 owner_id 是否始终分离？伪造别人的 owner 能否混过代理验签？ | 11 §1、3–4、6 |
| 期限 | 默认 365/可选 30、90 链日，最大 365 链日、锚点、24 小时发布期限、上界排除是否一致？重组后的锚点处理是否充分？ | 11 §2 |
| 授权排序 | 锚点较早的 GRANT 延迟发布、同锚点冲突、钓鱼签下的控制消息能否压过 owner 之后的撤销？锚点被重组移除时怎样处理？ | 11 §2、5 |
| 逐 owner 验证 | A 授权到期、B 未到期，同一 key 的新票是否错误覆盖 A 的旧票？ | 11 §6、8 |
| 恢复 | 被盗 key 连续签票或钓鱼 GRANT 生效后，owner 能否接管并撤销？节点落后的恢复页面会不会签出锚点更低的撤销？先撤销再换 key 时乱序上链会怎样，GRANT+CANCEL 能否一步到位？安全撤销后是否会回退旧票？ | 03 §6，11 §5–6 |
| 选票排序 | 中间改票未发布时，最新改票能否换中继单独发布？被扣留的早签票能否压过之后的改票？同一块内的两张不同票是否判冲突？客户端取低于最新块的锚点会怎样？锚点被重组移除时怎样处理？ | 03 §6，11 §6 |
| Adapter | 收窄提案格式清单能否复活已撤销的授权？新增控制格式是否不追溯？新增或停用 key adapter 是否不影响已有授权？ | 03 §5.1，11 §2、5 |
| 自然到期/主动撤销 | 到期、STOP_ONLY、安全撤销、授权冲突、换 key 的已有票语义是否区分清楚？ | 11 §5–8 |
| 时间与资格 | 两种票是否都检查完整 `[start,end)`？YES/NO 收录时资格与最终权重是否分开？ | 03 §4、6、8 |
| 完整历史 | 投票前的授权、已消费载体、全部存取款和重组能否重建？是否偷偷信任公共 API 全集？ | 03 §7、9，11 §7 |
| 官方认证 | 仅向运营方地址创建输出，能否伪装正式提案或结果声明？ | 03 §3、7，08 §2.1 |
| 流程角色 | 初始角色配置的来源、ROLES_UPDATE 签名链、准入必须早于开票、开票确认块数是否确定且无法被单方改写？旧流程记录被原样重发或扣住后首次发布，能否覆盖新状态？ | 03 §3、§3.1 |
| 结果一致 | result_core 与证据包是否分离？不同语言能否算出相同核心结果？ | 03 §11 |

| 密钥与镜像 | 在线钱包 key 身份与显示是否正确？重连、账户切换、清网页缓存、钱包丢失及镜像故障如何恢复？站点恶意脚本或其他网站可诱导什么签名，owner 能否及时发现？本机/通用 passkey 若开放，是否另审存储/备份/RP ID 风险？ | 11 §4 |

## 3. 什么已经检查，什么尚未验证

本轮做文档一致性、相对链接、章节目标、JSON 示例语法、代码围栏和文件 hash 检查；确认旧研究模型未改动。检查计数和文件指纹见 [design-audit.json](../research/design-audit.json)，检查范围见 [07](07-completion-audit.md)。

旧模型的 39 项测试和 1,000 份随机历史只覆盖其抽象输入下的既有计票性质。它不实现当前 V2 线格式、GRANT/REVOKE、安全撤回屏障、passkey、密钥保管、真实验签或链扫描。本轮没有重跑旧模型来冒充新功能测试。

**2026-10-08 实现更新：** 上述清单中的若干项已有可执行证据，见 [14：实施进度](14-implementation-status.md)：

- 机器 schema 与跨语言向量；
- 控制与选票状态机实现、场景测试与性质测试；
- 两套独立实现：同一模型写出，独立性有限；
- 开发链上的完整回放、重组测试与端到端演示。

评审实现时可从 [13 §4](13-technical-plan.md) 第 9–22 条（实现时补定的编码规则）和 `verifier-ts/SPEC-NOTES.md`（第二实现遇到的规范歧义）入手。仍缺的是真机签名、真实节点与主网规模的验证、人工审计和用户演练。

上线前仍须完成：机器 schema 与跨语言正负向量、控制/选票状态机实现与性质测试、两套独立 verifier、真实节点完整性和重组测试、在线钱包 key adapter 与真机显示/签名、用户与全站免费故障恢复演练、影子投票。本机密钥若另行开放，增加独立密钥库审查；通用 passkey/复杂 lock 未验收就不开放，不能把设计中的候选当成全钱包承诺。

## 4. 建议反馈方式

每条反馈写清文件与小节、可重现的消息/链位置顺序、目前规范会得到的结果、期望结果、影响和建议。区分协议错误、歧义、体验问题、治理待确认与可选优化；不要用“两个 RPC 一样”“已经上链”或“已有 N 人确认”代替完整性证据。

评审通过意味着可以按经修订的规范进入实现与 PoC，不表示主网可用、全部钱包已支持或金库可以据此自动打款。
