# 关键分支：哪些保证值得付出哪些成本

本文件补充 [主设计](02-design.md)，讨论没有选为默认的方案，以及条件改变后应该如何改选。A/B/C/D 沿用主设计定义。它们不是简单的安全等级：D 的合约可以正确拒绝双计，仍可能让漏票的结果被结算；B 可以重建已上链选票，仍无法保证所有人都赶上上链。

用户本轮已选 B 为设计基础；以下 A/C/D 保留供边界变化时评估，不能被实现者当作无需说明的自动降级。

## 1. 先把“可验证”拆开

| 要验证的问题 | 需要什么证据 | 什么证据不够 |
|---|---|---|
| 这张票属于这个存款主体 | scoped signature、正确 lock adapter、必要历史授权状态 | 只有登录签名；只有任意交易 input 的地址 |
| 本金在规定时点有效 | 创建与花费历史、准确 DAO 状态、规范链锚点 | 当前余额；只有创建交易 inclusion proof |
| 某张票已被发布 | 完整 envelope、位置和 inclusion | 只有后台 success |
| 所有及时有效票都被计算 | 可枚举的完整提交集合、确定性处理、完整历史边界 | 对运营者提供的十张票算得很准 |
| 结果应用了正确规则 | 固定 manifest/profile、正确整数运算、可重跑 verifier | 单个根哈希或“开源”标签 |
| 结果能强制支配金库 | 执行合约验证必要条件，或既有治理执行者审查 | 后台签名的通过证书 |

首版目标是前五项；第六项继续沿用 DAO 执行流程。选择信任后台的方案也可以，但应逐项说清后台究竟被信任做什么。

## 2. A：全部选票放在公开链下日志

### 2.1 可以认真交付的最小版

用户仍签 [协议草案](03-protocol.md) 中的选票；中继立即返回签名 receipt，并把完整 envelope 加入只能追加的日志。日志包括连续序号、前一条 hash、当前条 hash、接收时间和周期性 checkpoint；提供完整下载、稳定分页和至少两个独立镜像。比较 checkpoint，可暴露日志分叉与事后改写。

余额仍可通过 CKB 历史独立重算，签名仍可阻止后台伪造选择。这里省掉的是每批发布交易与等待链收录的成本，不是正确验签和 DAO 索引。

A 的时窗可定义为指定服务在 UTC 截止前签出的有效 receipt；结果须包含所有按政策认可的 receipts。**这明确依赖服务的时钟、及时接收和不偷偷出具回填 receipt。** 镜像及时见证能改善可观察性，普通 HTTP 日期或服务端 issued_at 不是独立可信时间。

### 2.2 故障与作弊

* 日志把 YES 改为 NO：原始签名验证失败，容易发现。
* 漏掉一张已经给 receipt 的票：用户可提供违约证据；须有固定争议窗口和处理程序。
* 用户只有自签选票，没有 receipt：无法只靠自填时间证明截止前曾送达。
* 后台截止后补发伪造接收时间：仅凭这个后台自己的签名无法排除。
* 多个镜像共用一个被裁剪的数据源：多个域名不增加独立性。
* 及时接收却选择性延迟公开：最终结果可能可复算，投票期间的信息公平性仍受影响。

A 需要明确的数据发布时限、责任主体、及时性见证和争议制度，不能等争议发生后再任意选择相信哪份截图或数据库记录。

### 2.3 值不值得加强 A

可以引入多方签署 checkpoint、独立收票节点、共同承诺 receipt 集合。若进一步要求拜占庭一致的统一日志，就需要成员管理、一致性协议、数据可用性和故障恢复。这不是“加三个签名”就得到的保证，也未必比现成的 CKB 公共链更轻。

定期把日志 root 上链能约束某个已知集合的事后改写，却不自动解决原文丢失、事先漏票和 root 发布前的时间回填。接受这种局部改善时，应逐项声明保证，不能宣传为所有选票链上可审计。

**选择 A 的条件**：急需替换旧前端，能接受明确的收票运营信任，签名导出和独立余额复算已经交付。若独立验证是主要目标且 CKB 已可用，B 更直接。

## 3. B：完整授权与签名选票公开到 CKB

### 3.1 三种数据布局

| 布局 | 优点 | 代价与边界 |
|---|---|---|
| 完整选票存在 output data | 结构直观，live indexer 初期容易展示 | 占较多 capacity；回收后仍须读历史 |
| **短 output header + 完整 witness** | 载体容量小且可回收，支持独立历史扫描 | 须取得 witness；不能只审计 raw transaction hash |
| output 只存 root，原文链外 | 链字节更少 | 增加数据可用性假设；原文被藏时 root 无法还原 |

默认选择第二种。交易费是发布成本，载体 capacity 是可回收周转资金，必须分开报价。投票频率较低时，省掉几 KB 可能不值得增加外部数据可用性协议；实际费用由 PoC 测量。

### 3.2 中继不是新的选举委员会

有效 envelope 不指定唯一中继。A 中继拒绝时可交给 B、普通帮助者或自己发布；重复出现不增加本金。链上没有“只有官方 sender 的票才算”的规则。

中继能决定免费额度，不能改变有效票定义。主服务同时控制索引和中继时，参考 verifier 仍必须直接读自己的节点。开放代码但没有可运行的备用发布工具，不能满足实际退出能力。

### 3.3 批量等待与截止

批量提高费用效率，等待凑满则增加截止失败。建议按时间上限或大小上限先到者发布，临近截止缩短等待；不以选择或票权决定顺序。客户端显示最新已收录状态，保留 envelope 供提前切换。

很晚的签名无法获得确定保证：拥堵、矿工选择和重组都可能阻止及时收录。提前提醒是运营缓冲，不能截止后以“早就点了按钮”为由改写收录时间。复核窗口只重算已有有效记录。

**选择 B 的条件**：需要公开可重建结果，希望保留一次消息签名的主要体验，可以承担链发布和节点运维成本，金库暂不要求合约自动执行。这与本次约束最吻合。

### 3.4 普通 carrier 与格式 marker

吸收此前评审提出的索引优化方向，但暂不改变首版默认：

| 选择 | 价值 | 必须承担的成本 |
|---|---|---|
| 普通 cell 短头 + 完整 witness（默认） | 无新脚本部署，任何代发者可按公开格式发布 | 发现载体需扫描相关历史区间；提供可重建的本地索引 |
| 加不可变格式 marker type script | 可用脚本索引查询 carrier 历史，减少发现数据的工作 | 代码 cell 容量、脚本审计、部署和依赖存续、索引完整性与版本管理 |

PoC 在相同历史范围比较首次同步、增量扫描、从零恢复、RPC 数量、磁盘和运行成本后再决定是否更换默认。不能只比较每笔手续费，也不能把暂占 capacity 当作消耗费用。代码按 hash 固定不自动保证代码 cell 永远可用，部署方案必须保证依赖长期可解析。

两种都保留完整签名 envelope，并允许任何 fee payer 发布；marker 只检查格式，不负责选民资格、收尾裁决或付款。自有索引需要涵盖已经消费的 carrier；第三方按脚本查询不能单独证明返回全集。若采纳 marker，在首个正式版本前固定载体与验证规则，不让同一 poll 中途改变。

## 4. C：用户直接签 CKB 投票交易

### 4.1 什么时候更好

某些钱包能可靠显示和签交易，却缺少消息签名接口；C 可能比复制长文本体验更好。公开链上也已有可重放的授权执行上下文。

但交易成功只说明 lock 的花费条件满足。ACP 免签路径、管理员路径或不覆盖 ballot commitment 的签名模式，都不能证明资产主体表达了投票意图。C 必须逐脚本、逐模式验证。[ACP RFC](https://github.com/nervosnetwork/rfcs/blob/62a6e08e16a995ab94562581978ceac3726c31e6/rfcs/0026-anyone-can-pay/0026-anyone-can-pay.md)、[Omnilock RFC](https://github.com/nervosnetwork/rfcs/blob/62a6e08e16a995ab94562581978ceac3726c31e6/rfcs/0042-omnilock/0042-omnilock.md)

### 4.2 只有 DAO 存款、没有零钱

消费 DAO deposit 会触发 DAO 状态转换，不能当普通找零。C 需要相同锁控制的普通资金 cell，或先建立这样的 cell；代付交易的组装、签名覆盖、找零和退款归属都须明确。[DAO 脚本](https://github.com/nervosnetwork/ckb-system-scripts/blob/72eb92fca090700dcb398cd8cad8fbd8bad40355/c/dao.c)

用户签完普通 sighash-all 交易后，中继不能随意再加入手续费输入。代付须按该 lock 的签名规则在签前协商交易，或采用另行审查的赞助协议。新建存款 lock、把本金转入投票合约，不属于本设计的“钱包适配”。

单 owner lock 自付模板保留为协议研究候选，不满足用户免费要求，不纳入首版已支持钱包入口。C 的赞助方案需完成独立安全验收后才可加入产品支持范围；上面的共同出资不是已完成的能力。无零钱用户优先使用 B 的消息签名加任何人代发，不借适配之名消费 DAO 存款。

### 4.3 cell_dep 能证明什么

要求 deposit 作为 live dependency 被解析，可核验交易执行时的本金。这不能证明截止余额，不能枚举 owner 的全部存款，也不能单独阻止多个 intent 重复声明同一 deposit。

存款非常分散时，将全部 outpoints 放进一笔交易会受体积、依赖和执行成本约束。deposit 后来被花费，结算时再次引用又会失败。必须先选清投票时余额还是截止余额，不能让能成功引用哪些 deps 反过来决定治理规则。

**选择 C 的条件**：核心钱包消息功能不足，目标 locks 的交易授权可安全识别，必须证明资金/签名覆盖安全，并由赞助者承担费用及周转容量，投票用户无需付费。满足这些条件后才可作为 B 共享语义的可选产品通道。

## 5. D：让合约验证最终结果

### 5.1 原生状态与分片

需要分别解决资格集合、已提交票集合、更新覆盖关系、聚合覆盖范围。每主体一个状态 cell 或 nullifier 可帮助唯一性，分片降低争抢，却仍需要可信或可验证的全集边界。

“全部已登记 shard 合并了”不等于“所有及时发布的有效 intent 都进入 shard 了”。若任何人可新建 intent，finalize 却只检查已聚合集合，协调者可能抢先关闭、漏掉别人的票。已有测试网明确保留此限制。[分片方案边界](https://github.com/anihdev/ckb-voting-dapp/blob/2af7bafb9e579de56b0103bad2dc1eab7eee4662/SHARDED_AGGREGATION_EXPLAINED.md#what-this-does-not-solve)

改进可以要求提交原子更新受约束登记状态，允许遗漏票在争议期阻止 finalize，或证明完整历史。每种都增加并发、截止、容量、退出和运维问题。若资产进入专用 lock，还增加本金合约风险和迁移成本。

### 5.2 zkVM 压缩历史验证

更适合与 B 衔接的是：公开链数据仍是事实源，将审查过的纯规则放进 guest，生成执行证明。证明至少须覆盖：

1. 网络、前后链锚点、连续区块及交易/witness 根。
2. 经过认证的初始 DAO 状态，或从已验证状态递归衔接。
3. 完整区间中的创建、花费、选票、授权和修改顺序。
4. 截止状态、精度、阈值、manifest 与结果。
5. 固定 guest/verifier 版本及必要公开值。

CKB header 不直接给出任意历史 UTXO 状态根。把某人提供的期初余额当 witness，再证明其上的七天计算，并没有证明期初余额是真的。[区块结构](https://github.com/nervosnetwork/ckb/blob/2592ddf0502cd4adfe886db893cccc866db3c60f/util/gen-types/schemas/blockchain.mol)

证明须锚定执行层认可的规范链，不能接受攻击者自造的内部连续区间。zkVM 证明不是 PoW fork-choice 的自动替代品。部署、证明系统假设、升级权限和 prover 可用性也须评审。

可先把证明作为独立复算的加速物，再考虑执行合约。没有证明时仍能普通重放；自动执行如何等待、超时或回到人工治理，必须事先固定。

### 5.3 乐观结果与挑战期

另一分支是发布结果并押金，允许公众提交反例。日常无需完整证明，但依赖至少一个及时在线、有数据且能负担挑战成本的诚实观察者。

遗漏已收录票可能有紧凑 inclusion 反例；声称 cell 截止时未花费、或某票是 owner 最新票，可能涉及区间完整性。不能假设每类错误都有很小且可在 CKB-VM 验证的挑战。需要具体欺诈证明、争议状态机、超时和恶意拖延分析；仅宣布挑战期不构成安全方案。

**选择 D 的条件**：需要合约强制执行，愿意投入额外审计与基础设施。仅替换投票工具时，收益不足以抵消复杂度。

## 6. 快照与“计算方式不变”

传输从 A 换到 B，不要求把票权时点也改掉。

| 策略 | 好处 | 兼容性边界 |
|---|---|---|
| 每次投票查询并永久冻结金额 | 接近旧平台描述的单次操作 | 跨时点相加可能重复使用流转本金，不能保留此漏洞 |
| 投票时授权 outpoints，截止剔除已花费项 | 本金可追踪，避免花费后双计 | 新增存款不自动计入，需更新选票 |
| **截止状态、汇总已投票 owner** | 统一结算、动态预览、防跨时点累加 | 新增存款扩大已投票主体权重，提款减少权重 |
| 开始快照 | 权重稳定，可预建完整表 | 新用户排除，退出者仍保留旧票权 |
| 最小余额、时长加权、额外锁仓 | 增加某些短期资本操纵成本 | 改变权重或资金约束，超出本任务 |

推荐第三种是技术与使用判断，**不是认定用户已授权改变规则**。先核对历史样本和社区确认，再冻结 profile。若最终选择第二种，B 的发布与大部分认证层仍可复用，计票及 outpoint 授权 UX 需要调整。

保留旧 bug 不符合“保持计算方式”的合理目的；未告知就换成开票快照同样不符合。应把公式、时间、资格与显示精度分别列出，逐项说明保留了什么、澄清了什么。

## 7. 核心性质与前提

在完整且正确的截止状态中，每个 live outpoint 只有一个 lock，每个 lock 最多取 YES/NO 之一。精确本金模式因此有：

```text
Y + N = 有最终 YES/NO 选择的主体所控制的合资格本金之和
      ≤ 截止时全部合资格 active deposit 本金之和
```

期限型授权不改变这个上界：先对每个 owner 解析当前提案的有效选择，再按其 deposit 计权；同一 key 代表多个 owner 不额外创造本金。控制冲突与安全撤回语义见 [11](11-authorization.md)。

这解释了为什么账号重复、地址显示格式和重复广播不应增加本金。对一张**已经有效收录**的相同 body 再广播，不改变最新有效选票或选择。原先无资格、后来有资格的重新提交，则是新的有效出现，不能被错误去重掉。

这个推导不证明输入真伪、签名安全或历史完整。它依赖真实 owner 映射、有效性判断、历史授权解析和正确状态集合；[研究模型](../research/README.md) 只检验这些前提下的处理。

## 8. 决策顺序

先冻结本金计算和兼容边界，做 Neuron 首次授权在线钱包、日常签票及 owner 恢复 PoC，并测独立重放成本；本机密钥库为可选研究，不作为首版依赖。按用户已选 B 推进，对确有需要的钱包研究满足用户免费要求的 C。若后来预算只能支持 A，须明确重新选择并说明接收和时间的运营信任，仍交付完整数据和退出路径。出现自动执行的实际需求后，再为 D 独立立项。

这样首版保持小范围，后续增强沿用公开证据和规则，不必每次换平台都重新信任一个身份数据库。
