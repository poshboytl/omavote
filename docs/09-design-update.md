# v0.3 修订与决策记录

修订完成日：2026-10-08。用户选择本套设计为基础，并在审阅 Fable v3 后确认采用有期限的重复使用授权，其余争议按本套设计取舍。本文件描述最终评审稿，不要求读者从旧对话或覆盖说明推断当前选择。主协议见 [03](03-protocol.md)，授权协议见 [11](11-authorization.md)，评审入口见 [12](12-review-guide.md)。

## 1. 当前基线

**浏览器 → owner 直接签票，或一次授权后的专用 key 签票 → 开放中继代付发布完整数据 → 独立历史计票 → 既有金库多签人工执行。**

| 决策 | 当前选择 |
|---|---|
| 票权 | Nervos DAO active deposit 本金线性计算；推荐截止状态，现规则歧义须正式确认 |
| 授权 | 首版支持一次授权、多次投票；默认一年（365 链日），可选 30/90/365 天，上限 365 个链时间日；没有永久授权 |
| Neuron 体验 | 每个存款地址首次签 GRANT 授权第二个在线钱包；同地址多笔存款不重复操作；有效期内连接该钱包为各 owner 签票，不必每次打开 Neuron |
| key 保管 | 主流程由在线钱包保管，投票站不接收私钥/助记词；逐 key adapter 验收；网页本机密钥为可选候选，通用 passkey 独立 PoC |
| 发布与费用 | 完整 policy、控制消息、选票与 proof 进入 CKB 历史；用户免费为硬约束，中继/运营方/帮助者承担链费与载体容量；备用发布不强迫用户付费 |
| 修改和恢复 | owner 直接票优先；授权控制、选票与流程记录都按签入的锚点排序，锚点一律取最新块，选票不设序号；控制消息按全局控制格式集合处理；GRANT 可一步撤回旧代理票；逐 owner 先验授权再排序；安全撤销不复活旧票 |
| 自然到期 | 停止新代理票，保留到期前已经有效投出的票 |
| 安全撤销 | 默认停止新票并撤回未结束提案中的先前代理票；owner 直接票和已结束提案不受影响 |
| 时钟 | 固定父块 MTP，完整开票下界和截止上界；链日不保证精确墙钟时长 |
| 载体 | 默认普通 carrier，不部署新 type script；marker 留给 P1 测量后独立决定 |
| 结果 | 数学结论、验证完整性、治理处置分开；统一 result_core，不要求跨实现证据包字节相同 |
| 金库 | 沿用现有多签人工付款，无本金迁移、托管或自动执行 |
| 首版范围 | 小范围固定规则；不预做自动延期、利息/年龄权重、Abstain、乐观投票或委托市场 |

换工具属于元规则事项，由用户和既有治理程序推动；软件提供影子投票、正式目录/状态和证据，不自行判断批准程序的合法性，也不新增人员白名单。

## 2. 本次吸收和修正

| 来源/问题 | 已写入的处理 |
|---|---|
| Metaforo 的一次设置习惯、Fable 的期限型 key | 11 给出 owner 控制消息、期限、验签、状态机和恢复；05/10 同步首次与后续体验 |

| 旧 GRANT 延迟发布、授权更换、撤销 | 控制消息按签入的锚点高度排序并有 24 小时发布期限；锚点较早者不能恢复旧授权；冲突和安全撤销形成明确屏障（第二轮评审取消了原 auth_sequence，见 §9） |

| 只检查不晚于截止 | 直接票和代理票均验证完整 `[start,end)`；过早出现不占序号 |
| 哈希上链即能删库恢复 | 核心规则与授权全文发布；附件哈希不替代可用性；私钥/待发队列/回执有单独备份责任 |
| 浏览器本地算等于完全验证 | 标明自身收录、给定材料验算与完整历史审计的不同范围；保留第二独立实现 |
| Ledger 首行缩短、passkey 换站 | 增加授权 key/期限的真机显示验收；RP ID/加密备份/owner 恢复不能被一键承诺省略 |

上一轮已吸收的可读票面、论坛导入、公开 API/feed、多地址进度、历史索引加速与钱包研究继续保留。Fable 原稿已于 2026-10-08 按用户要求删除，本套文档是唯一规范。

## 3. 版本和体验变化

文档从 v0.2 更新为 v0.3。由于代理票字段、nonce、控制消息和载体 kind 改变，未部署线协议从 V1 草案转为 V2 草案，使用新的签名域与格式；没有已上线数据需要迁移。不允许同时宽松接受旧 JSON/旧可读格式。

对 Neuron 用户，主要负担移到首次授权、到期续期和密钥恢复。A、B 两个地址授权同一在线钱包仍需两份 owner 签名；以后连接该钱包为两个 owner 分别签本提案的票。网页可以合并引导，实际钱包弹窗次数按 adapter 验收公布。已签的不同地址仍可能分批收录，页面逐地址标明未完成部分。

每次投票仍产生具体提案签名；没有恢复成服务器账号记一行票。授权 key 不需持有 CKB，存款不动，已支持的正常与恢复路径由中继/帮助者承担费用。外部发布者可自愿用自己的普通资金承载；C 自付模板只作研究候选，免费赞助验收未完成前不能算首版已支持入口。

## 6. Claude 评审后的 A–E 决策

2026-10-08 用户确认以下选择。此表的字母是评审问题编号，与架构路线 A/B/C/D 无关。

| 评审问题 | 当前决策 |
|---|---|
| A：授权期限 | 默认一年（365 链日），界面可选 30 天、90 天、一年；不提供 180 天预设或永久授权。UI 预设不进入 policy/rules hash；已有授权仍按其已签到期时间生效 |
| B：尾盘只收直接票 | 首版不启用：rules_profile 预留 `delegate_cutoff_ms` 并取 0，不设代理票提前截止（§10）。以后若采用，须经规则确认，由新的已确认 profile 冻结代理与直接票各自的时间窗，不能临时开启 |
| C：流程签名人 | 采用独立流程签名密钥与明确阈值；委员会沿用既有治理认可的阈值，协调者使用自己的流程密钥。格式已写入 [03 §3.1](03-protocol.md)：初始配置写入切换元规则提案并作为部署参数固定，变更由委员会阈值签 ROLES_UPDATE；流程密钥没有金库资产权限 |
| D：Neuron 改进 | 并行评估批量消息签名与 dApp 连接；Omavote 首版不依赖外部钱包先交付。此决定不代表已向钱包团队发送请求 |
| E：切换与规则澄清 | 支持由用户把工具切换与截止快照、phase-1、精度、67% 边界和时钟澄清打包为公开元规则提案；逐项列明差异，软件不代替治理批准 |

B 的候选机制例如：七天投票的最后 12 小时，拒绝新的代理票与代理改票，保留此前已有效代理票，继续接受 owner 直接 YES/NO/CANCEL 和及时授权撤销。12 小时仅为说明，不是已选择参数；截止本金仍在总窗口结束时结算。存款 owner 自己签票属于直接票，是否由中继发交易不改变这个分类；浏览器钱包若直接控制存款 lock，也可以签直接票。

Claude 评审发现的隐藏高序号 GRANT 压过撤销、控制序号耗尽、提案创建签名/流程角色未完整定义、确定性开票确认与 Ledger 显示等问题，当时仍待修订。第二轮评审后已写入规范（§9），同事复核后的修正见 §10；它们尚未经过可执行模型或实现验证，11 §8 的预期场景仍不是已执行测试。

## 7. 用户免费投票的明确约束

2026-10-08 用户确认继续保持 Metaforo 的免费投票体验。此前 B 主线一直由中继代付，但“用户可自费兜底”及 C 自付候选容易被解释成故障时要求选民付费，现已明确排除这种产品要求。

已支持用户的授权、续期、YES/NO、改票、CANCEL、撤销和恢复必须免费；发布链费与载体容量由中继/运营方/帮助者承担。投票 key 和存款地址都不需要用于投票的普通余额。正常及应急界面不要求用户充值、付款或预备周转 cell；所有免费发布方不可用时明确显示未完成与服务不可用，不用收费替代服务。

协议仍允许任何外部发布者自愿出资发布合法消息，票效力不取决于谁付钱；这不构成对投票用户的付款要求。C 的单 lock 自付模板仅保留为研究候选，免费赞助与签名覆盖验收未通过前不得标为已支持产品路径。运营预算、公平限流、免费恢复预算和备用赞助演练进入交付门槛。此项只明确产品与运维要求，不改变票权、签名对象或有效选票判定。

## 8. Neuron 与第二个在线钱包的主流程确认

2026-10-08 用户确认采用第二个在线钱包作为 Neuron 用户的日常投票入口。此前文档把网页生成本机 key 作为首版必做项，现已同步调整：

1. 首次连接一个已验收的在线钱包，以其保管的 key 作为日常投票 key；不转移存款，不导入 Neuron 助记词，不要求在线钱包有 CKB。
2. 每个 Neuron 存款 owner 用 Neuron 签一份 GRANT，明确目标 key 与期限；默认一年（365 链日），可选 30/90 天。同地址多笔存款只需一份授权。
3. 授权有效期内，打开提案、连接同一在线钱包、选择并签具体选票；中继免费发布，不必每次打开 Neuron。连接或登录本身不算投票，多 owner 仍分别签票和验权。
4. 续期、换成不同 key、安全撤销或直接接管时再使用 Neuron；这些发布同样免费。清理网页缓存后可重新连接钱包，并从公开历史恢复授权信息，网站不承担钱包私钥找回。

网页生成本机密钥保留为可选候选，不作为默认设置或首版依赖；若开放，单独验收保管、浏览器留存、恶意脚本风险和恢复。在线钱包清单、签名显示、弹窗次数及镜像重连依实际 adapter PoC 发布，不把任何候选钱包说成已支持。这次变更调整产品主路径及验收范围，没有改变控制消息线格式或修复 §6 列出的协议冻结阻塞项。

## 9. Claude 第二轮评审后的规范修订

2026-10-08 主流程确认后，Claude 第二轮评审发现 §6 列出的冻结阻塞项仍未修复，在线钱包主路径还带来新的风险。用户要求直接修改，本轮写入下列规范修订：

| 问题 | 修订 | 位置 |
|---|---|---|
| 控制消息只按 auth_sequence 排序：一份被钓鱼签下的最大序号 GRANT 使 owner 再也无法撤销，延迟发布的高序号 GRANT 能压过之后的撤销 | 取消 auth_sequence，控制消息按签入的锚点高度排序；同锚点不同 body 为冲突；owner 之后签出的任何控制消息都能生效 | 11 §2、5 |
| auth_policy 包含 adapter 列表，每接入一个在线钱包都会迫使所有 owner 重新授权 | policy 只含语义；adapter 改为不可修改的版本化 ID，由每个提案的 auth_registry 列出接受者；评估提案时只采用这些 adapter 签署的选票与控制消息 | 03 §3、5.1，11 §2、5–6 |
| Ledger 只显示前 61 字节，原首行是固定标题 | 选票、授权、提案与流程记录的首行改为不超过 60 字节的 ASCII 摘要；GRANT 增加 Key-Address 行 | 03 §3.1、5，11 §3–4 |
| 提案签名与流程角色未定义 | 定义提案签名文本、角色配置、ROLES_UPDATE 签名链、六类流程记录及载体 kind 6/7 | 03 §3.1、7 |
| 开票确认不是确定性规则 | manifest 收录块与开票块至少相隔 `opening_confirmations` 块，否则为 LATE_MANIFEST；准入记录须早于开票 | 03 §3–4 |
| 选票序号可被一次签满 | 两条选票序列都不许跳号，跳号出现为 SEQUENCE_GAP | 03 §6，11 §6 |
| 通用在线钱包会被其他网站请求签票 | 引导独立投票账户、每张代理票提示 owner、验收签名弹窗显示来源；B 可提供额外缓冲 | 11 §4.2，05 §2.2 |
| GRANT 的目标 key 用户无法核对 | 按 key 所在钱包的显示形式渲染 Key-Address 与缩写 | 11 §3–4 |
| 重连钱包后无法按 key 找回授权 | 增加按 key_id 查询授权、按 owner 的 feed 与流程记录接口 | 03 §12 |

另在 rules_profile 预留 `delegate_cutoff_ms`（首版为 0），以后启用 B 只需新的已确认 profile，不改线格式；同一 key 一次签名覆盖多个 owner 留作将来可新增的签名格式。

> 注：上表第 2 行“评估提案时只采用这些 adapter 签署的选票与控制消息”与第 6 行“选票序号不许跳号”经同事复核发现缺陷，已在 §10 修正；本节当时列出的待确认事项与冻结说明也由 §10 和 [05 §8](05-delivery.md) 取代。

## 10. 同事复核后的修正

2026-10-08 同事复核 §9 的修订，指出两处需要回改、两处表述过宽。用户要求纳入合理部分，并以本目录为唯一设计基线。本轮修正：

| 复核意见 | 修正 | 位置 |
|---|---|---|
| 按提案清单过滤控制消息，后续提案可能忽略已发布的撤销，使旧授权复活 | 控制消息按全局、只增不减的控制格式集合处理，提案清单只过滤选票。不变量：收窄清单不会复活授权；无法识别的控制格式报告不完整，不能跳过 | 03 §5.1，11 §2、5 |
| 选票不许跳号，使最新改票依赖中间版本先发布 | 取消该规则：选票签入锚点，按 `(锚点高度, sequence)` 排序，代理票先比较 grant 锚点。最新改票可单独交给任何发布者，被扣留的早签票也不能压过之后的改票 | 03 §5–6、12，11 §6 |
| “之后签出的任何控制消息都会生效”不准确 | 改为“锚点更高、有效并及时收录”；补充恢复客户端的同步检查、锚点选择、收录后核对与重组重签 | 11 §2、5 |
| Ledger 首行只是有限显示保证，64 位编号不等同完整哈希 | 列明设备上看不到、须在电脑端核对的字段；改写 2^64 的表述 | 03 §5，04 §3.1，05 §2.2，11 §3–4 |
| 准入记录没有确认深度 | 准入记录与 manifest 一样，至少早于开票块 `opening_confirmations` 个块收录 | 03 §3–4、§3.1 |
| 冻结标准说得过宽 | V2 冻结条件写入 05 §8：状态机实现与评审反例、乱序与重组组合、性质测试、机器 schema、跨语言与真实签名向量、首版钱包 PoC | 05 §8 |

同事对待选项的建议一并纳入：

* 首个在线钱包：MetaMask 类 EVM EOA 做首个 PoC，重点验证手机连接、全文显示与多地址签票；最终支持范围以 PoC 为准。
* B：首版不启用（`delegate_cutoff_ms = 0`），以后启用须经规则确认。
* 流程角色：成员名单与阈值沿用既有治理确定的结果，在切换提案中固定初始配置；验证报告注明初始 `roles_hash`。
* 开票确认：100 块只作测试候选，不代表已证明安全。

## 11. 第二次同事复核后的修正

2026-10-08 同事复核 §10 后，指出三个问题：流程记录可被旧声明覆盖，锚点保证仍然过强，撤销后换 key 存在先后问题；另有两处残留。用户确认了两个设计取舍：删除选票的序号字段，允许 GRANT 一步撤回旧代理票。本轮修正：

| 复核意见 | 修正 | 位置 |
|---|---|---|
| 流程记录按最后收录决定状态，旧声明可被原样重发，或扣住后首次发布，覆盖新的治理状态 | 流程记录签入锚点与发布期限（协议常数，候选 72 小时）；同一 record_id 只认首次有效出现；同一 poll 的同类记录按锚点取最新，同锚点内容不同为 RECORD_CONFLICT；ROLES_UPDATE 同样受发布期限约束 | 03 §3.1 |
| 允许取 tip 之前的块作锚点，后签的改票可能输给被扣住的早签票；同锚点内被隐藏的高序号也能反超 | 选票与控制消息的锚点一律取签名时已验证的最新块；同一序列两次签名之间等出新块；删除选票的 sequence 字段，同锚点、内容不同即为冲突；保证改为如实表述 | 03 §5–6，11 §2、6 |
| 先签撤销、后签新 GRANT 时，若新 GRANT 先上链，撤销会被判过时，旧代理票保留 | GRANT 可带 `revoke_mode = STOP_AND_CANCEL_OPEN`，一步完成换 key 与撤回；单独撤销后须确认生效，才生成新 GRANT | 11 §3、5 |
| 规则参数仍写“最高 sequence”；11 §4.2 仍写尾盘机制待决定 | 改为按锚点；尾盘机制改为首版不启用 | 03 §4，11 §4.2 |

同类问题一并修正：11 §2 原先允许普通 GRANT 取 tip 之前的块，被扣住的钓鱼 GRANT 同样能压过 owner 之后签的正常 GRANT；现已与其他消息一样取最新块。GRANT 首行摘要的到期日前缀由 `UNTIL` 改为 `TO`，带撤回时写作 `OMAVOTE GRANT+CANCEL`，最长 59 字节。

代价：同一地址两次改票之间要等出新块（约 8–10 秒）；锚点块偶尔成为孤块，须重签；两台设备在同一块内签出不同选择，会成为冲突。05 §8 的冻结条件仍全部待完成；本轮没有修改研究模型或任何实现。

随后按复核意见补两处：RESULT_ATTESTATION 的 `outcome` 必须与 `result_hash` 所指结论一致，不符即显示争议；控制格式被攻破后“伪造授权下的选票不被计入”只在提案清单已排除该格式时成立，仍接受它的提案须暂停执行并按治理处置（03 §3.1、§5.1，11 §5）。
